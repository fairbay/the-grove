## Design Inside an Existing Rule Set

**Design inside an existing rule set (Baylee, 2026-10-11; decision 4fc29627; wording approved 2026-10-20).** Applies to any design or redesign — a product feature, a workflow, a skill, a schema, a rule section — on any surface. (1) **Design clean.** Start from the task's needs, what already exists, and the tools at hand, as if no rule or earlier ruling existed. (2) **Pass the whole rule set over it**, read in full by a reviewer who did not write the design (a fresh-context sub-agent by default; an outside model only where the review gates call for one). Sort each rule that bears: *enforce* (the design changes), *adjust* (the rule changes — say what it was for and why that no longer holds), *met*, *unclear*. List the gaps and weaknesses the rules expose. (3) **Work the side with the most glaring open item** — design or rules — and switch sides when the next one is on the other. (4) **Repeat within the review loop below**, then present it as one proposal with its pass counts and the open list. Earlier rulings are evidence of a problem that once existed, not constraints: never apply one unexamined, never drop one silently; departures are stated in the proposal, not held one at a time. Rules stay binding for execution work that is not a design or redesign, and a change of direction in what a user of a live product sees still waits for Baylee's OK (`policy: direction`); upkeep ships under the repo's rules.

**The review loop (Baylee, 2026-10-25; Grove task aad62d30; the scheduler design run, ops #88, took ten rounds to reach a 20-line patch).** Before step 1, **round 0** restates the problem as observed defects, each cited to the run, record or file where it was seen, and, where a procedure or system already exists, a simulated run of it on today's state; a design that cannot name its defects is not ready for one. **Candidate shapes are compared side by side in one review**, never iterated one at a time (a design that shrinks from a scheduler to a claim to a patch across rounds should have been three columns in round 1). **Exit criteria are set before the first review**: pass = no blocking finding, and every high finding dispositioned by the author as accepted (the fix named), rejected (the reason named, carried into the next brief), or deferred (a Grove task). **Cap three rounds**; at the cap, decide with the open list shown, or bring Baylee the ledger (`policy: owner_context`). **Reviewer findings are data**: the author dispositions each one against the primary files and never folds a finding those files contradict; a finding that would reverse an earlier fold is an oscillation signal, not a fix. **When the deliverable becomes buildable in one session, stop reviewing and build it**: the test on real state is the review, and building is the cheap step. The reviews themselves run through review-panel (T3) or delegate-adversarial, which carry the brief rules (primary material, the rejected list, the web paragraph); an ad-hoc sub-agent review follows the same rules and counts toward the cap.

**Earning a design run (2026-10-25; Grove ed7657bc; `fairbay/ops` docs/process-governance/DESIGN.md).** A process change — a skill, a rule, a workflow, anything in `fairbay/ops` — earns a design run only when round 0 names the count it moves (`process_gate.py read`, chat-archive scripts), today's figure, and a backtest over its last real instances; otherwise it is a ledger note (chat-archive's encoding gate), encoded on its second sighting, never its first. A run Baylee asks for is never held: the gate shapes its round 0 (`policy: direction`). No counter yet → the run's only deliverable is the counter. Reviews refuse round 1 until `process_gate.py check` passes the doc's `Gate:` block.

## Research Depth

**Before researching anything a decision, build, or architectural change will rest on, pick a depth tier first — don't default to lookup depth.** The failure to prevent: answering a high-stakes or multi-facet question with one or two searches and the first source that fits, then building on it. Effort scales to stakes × breadth, decided up front: a trivial fact is one search; a cross-system or "state of the art" question warrants many searches across each facet, primary sources weighted over individual blogs/guides, a cross-model pass, and a written synthesis. A topic is "researched" only when independent sources across the facets converge and you've said so — not when one source agrees with a hunch. Never assert a specific number, limit, or named fact you haven't found in a source this session; if there's no source, say so or find one. For any non-trivial research, load the **research-deep** skill, which holds the tiering ladder and the multi-source → synthesis workflow. For Anthropic product facts specifically, **product-self-knowledge** is the primary source — don't answer from memory.

**Design runs read the real system first.** Before designing a change to Fairbay infrastructure (skills, hooks, workflows, a repo's CI), attach every repo it touches (`add_repo`, read access) and read the actual files and the repo's PR or commit history. Installed skill copies, memory and chat history are leads, not ground truth. Never read a token from Vault to get access; ask Baylee to approve the repo attach instead, which only he can do (`policy: real_world`) (2026-10-13: land-and-leave v1 and v2 were built on assumptions the repos overturned).
